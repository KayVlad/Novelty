# M1 LAN save sync implementation plan (2026-10-10)

This follows [the save/sync RFC](novelty_sync_rfc_v0.4.md). M0 stores portable save roots, verified immutable snapshots, an applied-head pointer and a verified local snapshot import with `available`, `current`, `ahead`, `behind` or `conflict` ancestry results. The real Template!! slot appears after restore and its bytes match the source; loading the slot in gameplay has not yet been explicitly confirmed. Network acceptance requires two devices outside the coding sandbox, which denies socket creation.

**Current implementation (2026-10-11):** `lan_connection.cpp` connects or accepts Qt TLS sockets, restricts certificate errors, and gates all application messages behind an exact trust pin or a two-sided phrase approval. `Window::devices` exposes manual-IP pairing and revocation. A trusted listener runs while the window has an available library. `lan_saves.cpp` supports exact-identity lookup, bounded snapshot file transfer and verified import. `lan_sync.cpp` fetches missing ancestors from a remembered trusted endpoint before ordinary UI or Steam-shortcut Play; the UI restores a single safe newer branch and preserves conflicts. Post-exit capture writes a durable per-peer queue and the window retries offers until an acknowledged receipt. Snapshot transfers use 64 KiB control-frame limits, 24 KiB binary chunks and a 512 MiB total cap; an unfinished transfer does not change the applied save head. Peer game ID links are explicit and scoped to a trusted fingerprint. The TCP integration fixture covers pairing, ancestry transfer and restore on socket-capable hosts; this coding sandbox skips its live part. UDP discovery, richer status, two-device acceptance and focused security review remain open. `lan_games.cpp` begins the M2 install path under the same trust layer, also pending TCP/device acceptance.

## Identity, discovery and pairing

1. Keep one profile per Games library for the initial release. Generate a unique P-256 device key and self-signed TLS certificate under that library's `.novelty/devices/` with owner-only private-key permissions. Use OpenSSL's supported key and X.509 APIs in-process; do not require an `openssl` executable or other installed manager. Package the linked TLS libraries with Novelty. The certificate/public key is the device identity; the local profile UUID is a namespace, not a shared login credential. **Implemented:** creation, reopen/relocation validation, exact-fingerprint trust/revoke storage and fail-closed damaged-record behavior. `configureDeviceTls` loads the certificate and P-256 key through Qt's path overload without requiring the missing local `QSslKey` header. A real TLS handshake still needs a socket-capable environment.
2. Discover currently open Novelty peers with a small versioned UDP multicast announcement. Advertise a random session ID and listening port only—no game titles, save paths, profile IDs, credentials or snapshot IDs. Show a clear manual-IP fallback if multicast is blocked. Discovery is optional and runs only while Novelty is open. **Implemented protocol primitive:** the strict 22-byte `NVD1` datagram codec and random session ID; UDP transport and UI remain open.
3. Use Qt's TLS sockets for the connection. During first pairing, request both certificates and allow only the expected untrusted/self-signed-certificate condition while keeping application data inaccessible. Derive a short, versioned verification phrase from both certificate fingerprints and fresh nonces, with canonical ordering and domain separation. Both people compare the phrase and approve on their own device. **Implemented protocol primitive:** `pairingPhrase` hashes the two certificate fingerprints with their respective fresh 256-bit nonces in canonical order and displays 80 bits as five groups of hexadecimal digits. The full TLS transcript, approval workflow and focused security review remain open. Never treat a user-chosen phrase as a password.
4. Store the approved peer certificate fingerprint and display name only within the current profile's data root. On all later sessions, require the pinned certificate and authorize every request against that profile's trust record. Revocation immediately removes access without deleting local saves. A changed certificate requires a new pairing, not silent trust migration. **Implemented helper:** a socket can authorize a peer only after encryption, self-signature/date checks, expected certificate-error checks and an exact profile-local fingerprint pin; wiring every application request to this helper remains open.

Qt documents TLS socket certificate/key configuration and peer verification in [QSslSocket](https://doc.qt.io/qt-6/qsslsocket.html); its documentation also cautions against blanket `ignoreSslErrors`. Qt documents multicast binding and group joining in [QUdpSocket](https://doc.qt.io/qt-6/qudpsocket.html). Key generation can use the supported [OpenSSL EVP keygen API](https://docs.openssl.org/master/man3/EVP_PKEY_keygen/). The exact handshake/SAS transcript must receive a focused security review before pairing is exposed as ready.

## Save exchange and lifecycle

1. Frame all TLS control messages with a version and length limit. **Implemented protocol primitive:** `NV` version-1 frames have a 64 KiB payload limit and a bounded receive buffer. Enforce per-request authorization, bounded lists and transfer quotas. Transfer snapshot manifests and file contents into a staging directory, verify hashes and declared portable roots, then call the existing import function. A transport failure leaves the current save and applied-head pointer unchanged.
2. Match peers by stable profile-game ID **and** confirmed game/edition/save-compatibility identity. Display names and VNDB metadata alone never authorize restore. Keep Proton prefixes, device paths and credentials out of transfer payloads.
3. Before Play, fetch an accessible peer head when online. If its ancestry descends from the local applied head, import and restore before launch; if both advanced independently, preserve both and prompt the user. If offline or a peer is asleep, allow Play and retain a durable pending sync task.
4. After the tracked game exits and local capture completes, enqueue the new head for each trusted peer. Repeated requests for an existing snapshot ID are idempotent. A peer that reconnects later exchanges missing ancestor snapshots and resumes queued work. The window shows local, pending, up to date and conflict states without implying success before acknowledgement.
5. Manual **Sync Saves** runs the same reconciliation, without adding duplicate snapshots. Never restore into a running game. The current `importSaveSnapshot` API performs safe local storage and ancestry classification; it does not establish peer trust and must only be fed by the authenticated transport.

## Test and release gates

- Unit tests: identity persistence and permission checks; exact TLS peer pinning/revocation; phrase agreement and wrong-peer mismatch; malformed/oversize frames; unauthorized catalogue/fetch refusal; snapshot replay, corrupted chunk, wrong edition, missing ancestor and divergent branches; offline queue persistence; no overwrite while running.
- Socket integration tests must run in an environment that permits loopback binding. This coding sandbox currently blocks even the existing local metadata fixture and umu's UDP socket.
- Two-device acceptance: Deck → desktop and reverse save/load, offline independent branches, sleeping peer, interruption during transfer, profile separation and revocation. No M1 completion claim until those pass.
- M2 game-folder transfer uses the same pairing/trust layer later. Server, accounts, login, WAN, relay and hosted game binaries remain outside MVP.
