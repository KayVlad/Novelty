# Novelty

A game lifecycle manager for Linux and Steam Deck, with visual novels first and support for other Proton games. Add a game folder or install the game, select its executable when needed, then press Play with suitable metadata and setup defaults. A sole suitable executable is selected automatically. Without a save server, a fresh LAN installation adopts compatible initial saves; later P2P replacement is an explicit **Transfer saves** action with Undo. An optional self-hosted server supplies automatic save sync.

Status: folder/installer import, executable choice, editable settings, prefix preparation, general and game recipes, cached VNDB metadata, local save discovery and verified snapshots are implemented. New managed libraries can prepare missing GE-Proton, umu and a known Steam Linux Runtime on first Play. LAN pairing, save exchange and staged peer game installation are implemented; live two-device validation remains open. A native portable test package can be built, while clean-device packaging and platform acceptance remain open. The maintained save contract and [hardening report](docs/reliability-hardening.md) are tracked under `docs/`; other planning notes remain local and ignored.

Steam Deck is the primary target; Bazzite desktop follows. Novelty uses progressive disclosure: simple defaults for ordinary play, with editable metadata, save paths, Proton versions and advanced configuration when needed. Stage 1 completes local installation/setup/play; Stage 2 adds saves and continuation across devices. Current folder import moves an external game folder into Games and prompts for an executable if detection is ambiguous or finds none. Cross-filesystem imports verify the copy and synchronize the destination filesystem before retiring the source; a cleanup failure keeps the registered destination and reports the retained original. The umu path supports DRM-free execution without a Steam client/account. Planned Steam support is a shortcut that invokes Novelty's managed launch.

The distribution target keeps Novelty-owned files in its application folder and the chosen Games folder. A user should be able to install Novelty, add a game and play without separately installing Bottles, protontricks or ProtonUp-Qt. External prefix tools remain optional. Removing a game or the app and its Games folder should cleanly remove Novelty-owned data. This is a packaging and storage acceptance goal; the current development build has not passed that gate.

Application preferences (selected Games folder, library view and automatic GE update checks) are read from and saved to `data/settings.json` beside the Novelty binary (`bin/data/settings.json` in the portable package). Each library owns its default recipe, fallback backend, runner and tool paths in `Games/.novelty/settings.json`. These files are authoritative; Settings edits the same values that can be edited in JSON. New files are populated from the opinionated JSON sources under `config/`, embedded during the build. Missing keys use those defaults; invalid values or malformed JSON report an error and keep the file available for correction. Library defaults are no longer written to SQLite. Existing SQLite-only defaults can be configured again in Settings.

For an app or OS reinstall on the same PC, back up the application's `data/` folder and the library's `.novelty/` folder along with the game files. Restoring `data/settings.json` restores app preferences; `.novelty/settings.json` restores library defaults, and `.novelty/library.sqlite` retains game configurations and Manage overrides. Keep private credentials and device keys private when backing up their folders. Paths to external files remain absolute and can be adjusted after reinstalling. Library-owned game, executable and runner paths are stored relative to Games and resolved when used; moving the complete library retains its settings, installation IDs and saves.

Implementation uses C++20, Qt6 Widgets and SQLite. The current build includes library discovery, executable/runner selection, per-game environment/arguments, prefix preparation and supervised umu launch. Add to Steam can create a shortcut that calls Novelty's managed launch. Settings can install pinned GE-Proton and umu versions with checksum verification; first Play can provision missing tools in app. Manage offers recipe presets plus supervised Wine configuration/registry tools and one-time patch/installer execution in the same prefix. Verified local save snapshots, guarded restore and LAN transfer use the same mapped save locations.

Automatic discovery waits briefly for new folders to stop changing before import. Each direct child of Games remains one game entry even when its executable is nested, for example `Title/Game/Play.exe` beside `Title/OST/`. Discovery searches nested folders for Windows `.exe` files and executable Linux ELF files or launch scripts, including files without an extension. A native Linux game launches directly, without Proton. **Add game → Select folder** also offers an explicit native execution choice and file picker; **Manage → Launch** can change the backend later. Novelty ignores hidden folders such as `.novelty` and prefers a game launcher over utilities inside soundtrack or runtime folders. Existing games remain available while this check runs. If a library disappears, reconnect it and use Rescan; the open window retains its entries. For umu and native games, renaming/moving the same folder within the Games directory follows its filesystem identity. Other moves use **Manage → Relink folder…**, preserving the installation ID and settings. Reopen the updated launcher and let the first scan finish before testing a rename.

Recipes live in `Games/.novelty/recipes/general/` and `games/`. Existing `default/` recipes are moved to `general/` when the library opens; user edits and stable IDs are retained. Older `engines/` files are kept on disk but are no longer selectable or matched. A game recipe may still inherit one of them so an existing library keeps working. Edit or import recipes in **Settings → Add or edit recipes…**. All files use schema 1, and `category` (`game` or `visual_novel`) is declared in JSON. `match.all` requires every condition; optional `match.any` requires at least one. Novelty tries game recipes, then the general preset selected in Settings. Multiple matching game recipes need a choice. Paths in recipes start at the imported game folder. An omitted `backend` means `umu`; `runner` accepts an installed exact version or a supported alias. Native Linux launchers are still detected and launched directly. Save discovery uses generic folder heuristics and explicit recipe save paths; engine configuration files are not parsed. `save_strategy` is obsolete: older recipes load with that field ignored, and new or edited recipes must omit it. Existing save configurations and snapshots are preserved. Ordinary recipe save paths and heuristic matches are candidates, including a sole match: confirm a location in Manage → Saves before it authorizes backup, restore or exclusion from a peer game transfer. Existing mappings are retained. An exact save rule tied to confirmed game and edition identities can still establish its declared locations automatically. Existing games retain materialized settings even when a recipe changes or disappears. Manage previews changes before a selected preset is applied, retains explicit overrides, and exports a portable manual game preset. Settings can export and import sanitized library defaults. The Steam Runtime app ID mapping is editable at `Games/.novelty/runtime-appids.json`.

Recipes provide the base launch configuration, including backend, runner selector, locale, arguments, environment, umu selector/game ID, store, Steam launch ID and requested components. Generic native executable detection remains part of discovery. Manage saves user overrides separately in the game record without changing its recipe file. Applying a recipe assigns its fields afresh, then reapplies explicit overrides, including cleared values. Existing games retain their applied snapshot until a preset is explicitly reapplied. **Export current preset** exports the saved effective settings; choosing the source recipe's ID exports a complete replacement with its matching rules, and selecting its file explicitly replaces it. Exporting to a library recipe directory validates the recipe and its filename before publication. Confirmed save mappings and snapshot history keep their existing storage.

Recipes can name one parent with `inherits`; child settings override scalars, merge environment keys, and add ordered, deduplicated `winetricks` verbs. Matching still uses only the child's own conditions. The built-in Game and Visual Novel presets explicitly leave the runner and umu selector empty to use the library choices, and request no extra components. Visual Novel inherits Game and sets `ja_JP.UTF-8` locale and `TZ=Asia/Tokyo`; Game uses the system locale. The configured library runner or an explicit game runner supplies the Proton version. A game recipe may request only `cjkfonts`, `corefonts`, `quartz`, `wmp11`, or `qasf` in `settings.winetricks`. Manage → Runtime can edit a game's requested components with the same allowlist. Play or Prepare shows the pending components and asks before changing the prefix. Headless launches wait for this approval. Novelty runs each approved verb through the selected GE-Proton/UMU-Proton bundle with umu, records completed verbs in `recipe.lock.json`, and retries only unfinished ones. Removing a verb from a recipe does not remove it from an existing prefix; a successful installation receipt does not mean the game was tested. Changing runners can also change the prefix and is not guaranteed to be reversible. For troubleshooting, try the configured runner first, then another exact GE version with a disposable prefix, then a demonstrated environment fix, and only then a justified component. Novelty does not cycle through these automatically.

For example, save this as `Games/.novelty/recipes/games/story.json` after reviewing its release markers:

```json
{
  "schema": 1,
  "id": "story",
  "name": "Story settings",
  "inherits": "general-vn",
  "category": "visual_novel",
  "match": {"all": [{"type": "file", "path": "Folder/Story.exe"}, {"type": "directory", "path": "Folder/game"}]},
  "settings": {
    "executable": "Folder/Story.exe",
    "runner": "GE-Proton11-7",
    "save_candidates": [{"scope": "game", "path": "Folder/game/saves"}]
  }
}
```

**Settings → Proton Manager** shows official releases and Novelty-managed GE installations in one list, with installed, available and installing states. Install any supported release with its row's **Install** button; **Load older releases** pages through the official catalog. Downloads use the upstream SHA-512 checksum and staged installation. The checksum detects corruption; it does not independently authenticate a compromised upstream release. Each managed installation has a **Remove** button in its row, with protections for selected, referenced and active runners. Installing a build keeps older versions and does not change the library default until Settings is saved.

Automatic GE updates are enabled by default. Opening a library starts an asynchronous official release check if its previous check was at least one day ago; there is no scheduler. Newer GE builds install alongside existing versions, with activity and errors shown in Proton Manager. The **Automatic check** checkbox disables automatic checks and installations. Play never joins a background GE installation: `ge-proton-latest` resolves to the newest fully installed, verified GE build already available, while exact versions remain pinned. An implicit GE choice on first Play follows the latest installed GE version too. If no matching installed runner exists during an update, Novelty reports that immediately. Changing a runner can affect an existing prefix; release-specific compatibility still needs real play, movie and save/load testing.

The separate **External Proton** tab provides a path field and **Add** button for either one Proton installation or a directory containing several versions. Steam Proton and Steam compatibility tools are discovered automatically; other launcher directories are never scanned automatically. Paths are canonicalized and duplicate installations appear once in the shared runner inventory used by Settings, Manage, recipes and first Play. External registrations live in `data/local-settings.json`; the automatic update preference lives in `data/settings.json`. Both stay outside recipes. Novelty never installs into, updates or deletes external installations; removing a registration leaves its files intact. An already installed registered GE release avoids a duplicate download. Missing explicit paths remain selected and are reported as unavailable. Floating `ge-proton-latest`, `proton-latest` and `proton-experimental` selectors can also be chosen directly in Settings or Manage.

Paired devices connect automatically while Novelty is open. Games available on a trusted device appear in the library with desaturated covers and **Not installed** status. Right-click → **Install**, or double-click the cover, to transfer a game; known saves travel through verified save snapshots separately. Install selects a local runner, prepares the receiving device's runtime and prefix, and applies one compatible peer save when there is no local progress, without starting the game. If setup is interrupted, Play retries it and continues with the peer save. Transfer addresses are remembered after authentication and rediscovered on the LAN when they change.

After installation, Manage → Saves offers **Transfer saves…** from a selected trusted device and **Undo last transfer…** when automatic server sync is off. Ordinary Play does not poll or apply P2P saves, including through a Steam shortcut. Verified empty saves can be transferred as intentional deletions. Settings can enable a self-hosted save server; the shared window/headless Play path checks accepted revisions and actual local files, uploads changed saves conditionally, allows offline Play, and preserves conflicts for an explicit choice in Manage → Saves. Pending sync and conflicts remain visible while idle; pending uploads retry while the window is open. Transport failure permits offline Play, while an incomplete local restore blocks launch until recovered. Tests cover the live local server, retry, conflict resolution and recovery barriers; TLS deployment and two-device acceptance remain open. Storage usage display, rolling retention and independent backup are follow-up work described in [the amended save RFC](docs/novelty_sync_rfc_v0.4.md).

For a local server trial, build `novelty-save-server` and run it with `--data /private/path`. It listens only on `127.0.0.1:42428` by default and writes an owner-only `access.token` inside that private data directory. It limits active requests to 64, requires headers within 10 seconds, and bounds authenticated transfers to 10 minutes in addition to the 30-second idle timeout. Use a TLS reverse proxy for another device, then enter its HTTPS address and token in Settings on each Novelty installation. P2P installations share a server game key automatically; independently installed copies can set the same advanced **Server game link** in Manage → Saves. The server limits heavyweight verification/archive work to two jobs. HEAD reads committed revision metadata; GET verifies payload contents. The server holds one current verified state per game key and retains earlier revisions for recovery; it is not an independent backup. Do not expose the plain HTTP listener directly to a network.

Pairing shows unverified machine names and the same six-digit code on both screens. Connect from one device and enter the code read on the other. On the receiving device, personally compare both screens, check the confirmation box and allow pairing. A remote approval message does not verify a human checked the code. Update both devices for the new code-pairing screen. Existing trusted devices, library identities and saved history remain valid; they do not need pairing again. Both clients must use compatible pairing modes; interoperability with older releases is not guaranteed. Cover previews are optional catalogue fields, so older peers can still exchange games without previews.

Build and run locally:

```sh
./scripts/build.sh
./run.sh
```

Choose the Games folder in Settings on first launch. The selected folder is saved in `build/data/settings.json` for the local build; later launches use that path. `--root /path/to/Games` can supply an initial folder before one is saved.

```sh
python3 scripts/install-umu.py /path/to/Games
```

This local build uses SteamOS's Qt 6.9.1 libraries; it is not yet a self-contained distribution. The script verifies a pinned upstream umu archive checksum and installs it inside the test library. A configured system umu installation also works.

## Reliability limits

Save snapshots, restoration, server publication and LAN game publication now use Linux file and directory durability barriers at commit boundaries. Cross-filesystem folder import persists the destination before retiring the source. Automated tests inject filesystem failures and process interruption; these establish software ordering and recovery behavior, not survival of an actual power cut on particular storage. Filesystem, kernel, drive firmware and hardware must honor flushes. Keep independent backups of valuable saves. Revision and snapshot retention is currently unbounded; no automatic pruning discards recovery data.

Run the Linux CMake/CTest suite with `bash scripts/build.sh`. CI runs the same test targets. Physical Deck/desktop, real LAN interruptions and homelab TLS/proxy/storage acceptance are still deferred. Back up saves independently and record baseline hashes before that campaign.

Recipe/Manage environment values use a shared supported-variable policy at validation and launch. Supported families include `DXVK_*`, `VKD3D_*`, locale `LC_*`, reviewed Proton/Wine options, `TZ`, and application data under `NOVELTY_APP_*`. Host loader, Python and shell startup controls are rejected with a named error. Existing configuration values are retained for review. Extending the list requires reviewing the new variable's host execution behavior. Steam shortcut paths containing shell expansion characters are refused without changing the VDF.
